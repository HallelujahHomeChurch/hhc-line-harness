# Durable entry and registration

Task 4 local implementation. `createRuntime` assembles the new Account/Asset/LINE adapters, transactional intake, interaction processor and registration domain. Task 5 wires this factory into the opt-in process entrypoint with source access and worker lifecycle; its database runtime mode remains closed by default. No real intake, Reply, provider or deployment has been enabled.

The raw signed webhook is bounded to 1 MiB and 100 projected events. Ordinary events are accepted only within 24 hours, after the runtime ingestion floor and within the active group interval. Receipts contain no raw webhook and expire after seven days. Source deadlines are exactly publication plus 2,160 hours. Receipt, permitted source, job and opaque wake record commit together; partial batch failure returns 503 and deduplication makes redelivery safe. Cleanup/restore fences are separately implemented in Tasks 5/11.

A group mention creates a 30-minute actor-bound bootstrap intent. Account login/binding continuation is owned by Task 6. Configuration requires current global Admin authority with Account actor, binding generation and authorization revision. Original-group preview additionally checks current LINE membership, exact Asset ACL/binding revisions, and a durable unique collection reservation. A five-minute single-use confirmation includes the same actor and group. Activation requires a successful single Reply attempt, fresh authority/membership/collection checks, unchanged local revisions and an atomic audit outbox commit. Unknown announcement outcomes remain inactive and require a new interaction. Global cross-service state is checked immediately around the operation; there is no distributed transaction between Account, LINE, Asset and Harness.

Replies use AES-256-GCM with delivery-bound associated data. A conservative 45-second event-age deadline is stricter than LINE's receive-time allowance. Reservation commits before network access and clears the stored token/content. A timeout, crash after reservation or unknown result never automatically retries. A new interaction can recover the setup; passive collection sends no Reply or Push. Interactive commands serialize per actor/scope through PostgreSQL; a stale command lease cannot commit setup or send a Reply. Crashed side effects are not replayed automatically.

Dependencies use fixed HTTPS origins, bounded 32 KiB metadata, two-second deadlines and no redirects or automatic retries. Account uses a dedicated private caller/token. A failed Account link event without a LINE source is ignored without inventing an actor; its challenge can expire safely. APIs follow the [LINE Reply contract](https://developers.line.biz/en/reference/messaging-api/#send-reply-message) and [account linking flow](https://developers.line.biz/en/docs/messaging-api/linking-accounts/).

Local checks: PostgreSQL-backed concurrency/rollback/expiry/authority tests, stubbed dependency contracts, typecheck, formatting and build. These are not external, device, Linux startup or CI acceptance. The restored runtime defaults closed; no command here opens it.

The dedicated Asset Harness collection picker returns collection metadata without ACL history. Collection detail returns only current ACLs, with at most 128 readers; overflow is rejected rather than silently truncating the approval audience. Only these two bounded collection responses use a 128 KiB JSON budget (other service responses retain 32 KiB). Revoked historical records do not consume the current-reader count. Other Asset callers retain their existing full-history contract. Deploy the owning Asset contract before enabling Harness setup.
