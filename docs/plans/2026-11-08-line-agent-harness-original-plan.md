# LINE 智能助理：完整架構與分階段實作計畫

## 一、目標與已確認原則

建立以 **OpenAI Agents SDK** 為核心的 LINE 智能助理，讓使用者可以自然語言找回群組曾經分享的資訊與附件。

典型情境：

> 成員貼了一張服事表，當時沒有呼叫 Bot。數週後，已註冊使用者問「@Bot 十一月最新服事表在哪」，Bot 找出資料，回覆原件、發布來源及版本依據。

固定要求：

1. **OpenAI Platform API 主用，Azure OpenAI 備援。**
2. 採 **OpenAI Agents SDK＋Responses API**；初期使用一個 Agent。
3. 個人必須註冊，才能使用智能體。
4. 群組必須另外註冊並告知成員，才開始收錄。
5. 群組啟用後，收錄所有成員的討論，包括未完成個人註冊者的發言。
6. 群組只有已註冊使用者 @Bot，或操作其授權互動按鈕時，才提供智能服務。
7. **不主動推播**；背景處理完成、定時工作、錯誤重試都不能自動發訊息。
8. 核心是資料保存、搜尋與原件找回；摘要只作搜尋輔助。
9. 個人與各群組資料隔離。
10. 不提供任意檔案系統、終端機或電腦控制能力。
11. 後端可受控保存及解析使用者提供的附件，不執行附件中的程式、巨集或指令。
12. 本計畫獨立設計，不參考既有專案。

## 二、第一版範圍

### 必須具備

- 個人註冊、群組啟用及服務管理人設定。
- 可靠接收、保存文字與支援附件。
- 群組內自然語言搜尋。
- 找回原件，附發布者、時間及來源。
- 辨別相關版本，遇到不確定時列出候選。
- 個人私聊與群組資料隔離。
- 撤回、停止收錄、刪除與保存期限處理。
- OpenAI 主用、Azure 備援。
- 每人、每群與全系統用量控制。
- 全程只使用允許的回覆機制。

### 暫不納入

- 跨群搜尋或私聊查詢群組資料。
- 主動提醒、定時發送摘要。
- 多智能體協作。
- 任意瀏覽器、檔案或電腦操作。
- 音訊與影片完整轉錄。
- 第一版直接代操作日曆、寄信等外部帳號。
- 自動回補 Bot 啟用前的群組歷史。

第一版優先做到「找對資料」。直接回答複雜表格中的排班內容，需在辨識品質驗證後逐步開放。

## 三、整體架構

```text
LINE Messaging API
        │
        ▼
事件接收層
驗證簽章、去重、可靠入列
        │
        ▼
註冊與權限判斷
        │
        ├── 收錄流程
        │      ├── 保存原始訊息與附件
        │      ├── 擷取文字／辨識圖片
        │      └── 建立全文與語意索引
        │
        └── 已註冊者呼叫流程
               ├── 建立目前群組／個人權限範圍
               ├── OpenAI Agents SDK
               │      ├── 搜尋工具
               │      ├── 資料讀取工具
               │      └── 版本查詢工具
               ├── OpenAI 主用／Azure 備援
               └── LINE Reply 回覆
```

建議初期以一個後端應用，分別執行事件接收與背景工作，不先拆成大量微服務。

| 元件 | 責任 |
|---|---|
| LINE 接收層 | 驗證原始 webhook、去重、可靠接收 |
| 註冊與權限層 | 使用資格、群組啟用、角色與資料範圍 |
| 工作佇列 | 附件下載、解析、索引及有限重試 |
| 資料庫 | 訊息、註冊、來源、版本、工作狀態與用量 |
| 私有附件儲存 | 原圖、文件及必要預覽 |
| 搜尋層 | 全文、條件與語意搜尋 |
| Agents SDK | 管理工具循環及回答流程 |
| 供應商整合層 | OpenAI／Azure 設定、能力與錯誤處理 |
| 回覆層 | 將答案轉成 LINE 訊息，禁止自動推播 |
| LIFF 頁面 | 註冊、設定及經授權的資料查看 |

搜尋索引可先與主要資料庫整合；是否另設搜尋服務，待資料量與效能證據支持後再決定。

## 四、註冊與群組啟用

### 4.1 個人註冊

流程：

> 私聊 Bot → 註冊入口 → LINE 身分驗證 → 確認使用規則與個人記憶設定 → 完成

要求：

- 後端驗證 LINE token，不信任前端提交的使用者 ID。
- LINE Login 與 Messaging API 規劃在同一 provider。
- 不以顯示名稱作為身分識別。
- 個人註冊一次，可在已啟用群組使用。
- 未註冊者呼叫時，只回固定註冊入口，不呼叫模型。
- 註冊成功顯示於頁面，不另外推播。

### 4.2 群組註冊

流程：

> 已註冊者在群組發起申請 → 回覆短效註冊入口 → 確認群組及申請人 → 設定管理人與規則 → 群組告知 → 確認啟用

要求：

- 申請憑證綁定群組、發起人、期限，且只能使用一次。
- 首次管理人認領由服務端政策授權，不能只靠持有轉傳連結。
- 管理人是 Bot 服務管理人，不宣稱等同 LINE 群組管理員。
- 保存啟用時間、規則版本、確認者及告知紀錄。
- 啟用前不建立聊天搜尋庫。
- 最後確認透過新的群組互動完成，以 Reply 回覆公告及啟用結果。
- 新成員告知由群組管理人維護固定公告，Bot 不主動通知。

公告內容包含：

- 收錄所有成員的新討論與支援附件。
- 用途是群組資料搜尋。
- 只有註冊者能操作 Bot。
- 處理供應商包含 OpenAI 與 Azure OpenAI。
- 保存期限、刪除方式、服務管理人。
- 不主動推播。

群組告知是產品流程；正式營運時仍需確認適用的資料處理要求。

### 4.3 狀態與停用

群組至少區分：

- 待啟用。
- 已啟用。
- 已暫停。
- Bot 已離群。
- 刪除處理中／已刪除。

暫停、離群後停止收錄；重新加入不自動恢復。停用與刪除是不同操作，介面要說明保存資料會如何處理。

## 五、資料收錄與搜尋

### 5.1 收錄原則

先可靠保存，再做較慢的分析。

LINE 文字無法於收到 webhook 後任意重新取得；媒體也不能依賴 LINE 永久保存，因此必須及時保存支援內容。[官方說明](https://developers.line.biz/en/docs/messaging-api/receiving-messages/)

每筆來源至少包含：

- 所屬個人或群組。
- 原始訊息識別碼與事件識別碼。
- 發布者識別碼、當時顯示名稱。
- 發布時間、收到時間。
- 文字、附件參照及內容雜湊。
- 可用的引用關係。
- 解析、索引、撤回與刪除狀態。

附件具有獨立狀態：

> 已收到 → 原件已保存 → 已解析 → 已索引

失敗時保留失敗階段及原因，不把「已收到」當成「已可搜尋內容」。

### 5.2 支援資料

| 類型 | 處理方式 |
|---|---|
| 文字 | 保存原文、全文索引 |
| 圖片 | 保存原圖，辨識文字與必要結構 |
| PDF | 優先擷取文字，掃描頁才做視覺辨識 |
| Excel | 讀取支援格式的儲存格，不執行巨集或外部連線 |
| 連結 | 保存網址與上下文；不自動取得未授權私人內容 |

加密、損壞、過大或不支援的附件需標示狀態，不宣稱已讀取。

文件內的指令一律視為資料，不能因此變更 Agent 規則、權限或呼叫外部操作。

### 5.3 搜尋流程

> 權限範圍 → 條件／全文／語意搜尋 → 少量候選 → 讀取證據 → 回覆原件

搜尋條件包含：

- 發布者。
- 發布日期與內容適用日期。
- 標題、檔名、資料類型。
- 圖片或文件內文。
- 相關說明與版本關係。

日期、姓名、編號使用精確搜尋；「服事表／輪值表／排班表」等不同說法由語意搜尋補足。

### 5.4 版本判斷

分開記錄「發布時間」與「內容適用期間」。

- 明確標示修正版：建立有來源依據的版本關係。
- 今天重貼舊表：不自動認定是最新有效版本。
- 不同活動的表格：不因名稱接近就合併。
- 無法確認：回傳候選及差異，請使用者選擇。

不因新版本出現就刪除舊版；在保存政策允許範圍內保留查核依據。

### 5.5 回覆形式

優先提供：

1. 找到的資料名稱。
2. 發布者與時間。
3. 適用日期及版本判斷依據。
4. 原圖、原連結或受權限保護的附件查看入口。
5. 不確定或缺漏說明。

可引用原訊息時使用 LINE quote token；不承諾所有資料都有可跳回原訊息的連結。[引用限制](https://developers.line.biz/en/docs/messaging-api/get-quote-tokens/)

找不到時說「在已收錄資料中未找到」，並區分尚未索引、超出收錄期間與沒有符合結果。

## 六、Agent 設計

使用 OpenAI Agents SDK 管理工具循環，模型經 Responses API 呼叫。SDK 執行於自己的後端，資料與權限由應用掌握。[官方架構比較](https://developers.openai.com/api/docs/guides/agents)

初期工具：

| 工具 | 功能 |
|---|---|
| `search_resources` | 搜尋已授權範圍的資料 |
| `read_resource` | 讀取候選內容與來源 |
| `get_resource_versions` | 查詢相關版本 |
| `prepare_resource_access` | 準備受保護的查看入口 |

限制：

- 使用者與群組範圍由後端注入，不讓模型自由指定。
- 每次工具執行都重新檢查範圍與資料狀態。
- 不向模型提供 LINE 憑證或推播工具。
- 限制工具輪數、輸出長度與總執行時間。
- Agent 依來源回答，不能將推測寫成正式決策或最新版本。

背景收錄採固定工作流程，不為每則訊息啟動 Agent。

## 七、記憶與權限隔離

區分三類狀態：

| 類型 | 用途 |
|---|---|
| 原始資料與索引 | 長期找回訊息及附件 |
| 衍生資訊 | 標題、標籤、版本關係、短摘要 |
| 短期對話狀態 | 處理「第二張」「那份有更新嗎」等追問 |

原始資料是證據，摘要不能取代原件。

固定隔離規則：

- 私聊只搜尋本人資料。
- 群組只搜尋目前群組資料。
- 管理人不能讀成員私聊。
- 不在私聊自動彙整群組資料。
- 快取、索引、附件、執行紀錄同樣遵守隔離。

多人同時提問時，依群組、提問者與互動關係追蹤短期查詢狀態，避免接錯話。

附件查看頁須驗證身分與群組存取資格；權限無法確認時拒絕提供，不能只依賴難猜網址。

群組中回覆的內容，所有當時可讀群組的人都可能看到。個人註冊限制的是操作資格，不是群組訊息的閱讀資格。新成員是否可查詢加入前的已收錄資料，需在上線前明確決定。

撤回／刪除應涵蓋原件、擷取文字、索引與相關快取；另定備份的淘汰期限，避免誤稱立即從所有備份消失。

## 八、Azure 備援

採主用／備援，不預設兩邊同時呼叫。

備援程序：

1. 判斷是否為可重試的暫時錯誤。
2. 在時間與預算內有限重試 OpenAI。
3. 確認 Azure 支援本次必要能力。
4. 從共同資料與已完成工具紀錄重建必要上下文。
5. 改由 Azure 接續。
6. 記錄供應商、用量與結果。

不因搜尋無結果、權限拒絕或安全拒絕而切換供應商繞過限制。

需要驗證：

- 模型與版本。
- Responses API、工具呼叫、結構化輸出。
- 圖片輸入能力。
- 區域、部署名稱、限額與延遲。
- SDK 實際整合方式。

不將 OpenAI conversation／response ID 或隱藏推理狀態視為可跨供應商共用。

文字與工具能力通過驗證、圖片能力未通過時，只能宣稱「文字備援可用」。兩邊共用總預算，備援不繞過額度。

Embedding 模型另外固定版本；不同模型的向量不能直接混用。索引服務故障時可降級為全文搜尋。

## 九、不推播與長任務

後端只開放核准的 Reply 發送路徑，不以提示詞作為唯一限制。

LINE reply token 有時間限制且只能使用一次，因此不能先回「處理中」，再用同一 token 發送結果。[官方限制](https://developers.line.biz/en/reference/messaging-api/nojs/#send-reply-message)

- 短查詢：在期限內一次回覆。
- 長查詢：回覆工作已受理及查詢方式，完成後只保存結果。
- 再次 @Bot：讀取原工作結果，不重新執行。
- Token 失效：不改用 Push。
- 背景索引完成：不通知。
- 指定時段：只安排索引或維護，不發送摘要。

Reply messages 不計入 LINE 方案訊息數，但模型、儲存與運算仍有成本。[LINE 計費說明](https://developers.line.biz/en/docs/messaging-api/pricing/)

## 十、成本控制

### 收錄成本

- 一般驗證、去重、文字保存不用模型。
- 相同附件在授權範圍內避免重複解析。
- 優先直接擷取文字，再考慮視覺辨識。
- 限制附件大小、頁數及支援格式。
- 不為每則訊息產生摘要。
- 不只保存 AI 判定有用的內容，避免日後重要資料已被漏掉。

### 搜尋與回答成本

- 先以權限、日期、姓名及關鍵字限縮。
- 只讀少量候選。
- 原件明確且回覆格式固定時，可直接組裝結果。
- 重用仍有效的解析與搜尋結果。
- 限制工具循環、輸入與輸出。
- 對話歷史按需要載入，不重送全群歷史。

### 額度與降級

分別設定：

- 每人互動額度。
- 每群索引與互動額度。
- 附件儲存配額。
- 全系統供應商預算。
- 單次工作上限。

超額時採明確降級：

| 狀況 | 行為 |
|---|---|
| 圖片辨識額度不足 | 在儲存配額內先保存原件，標示待辨識 |
| 語意索引不可用 | 保留全文與條件搜尋 |
| 模型問答額度不足 | 固定格式告知，必要時提供無模型的基本搜尋 |
| 儲存配額不足 | 標記收錄失敗，不假裝已保存 |
| 供應商皆不可用 | 保留工作狀態，等待使用者再次查詢 |

以實際 token、工具、重試及儲存用量核算，不只計算請求次數。每次工作啟動前預留預算，降低併發造成超額的風險。

日誌與 SDK tracing 需控制內容收集及保存期限，避免群組資料額外流入不必要的診斷紀錄。

## 十一、分階段實作計畫

每階段通過驗收後才擴展下一階段，不以「已設定」代替「已驗證」。

| 階段 | 工作與交付 | 驗收條件 |
|---|---|---|
| 0：規格與能力確認 | 決定保存政策、預算、首次管理人認領方式；驗證 LINE 與兩供應商能力；建立去識別測試資料 | 確認可接收的附件、模型能力及限制，不承諾未驗證功能 |
| 1：註冊與權限骨架 | 個人註冊、群組啟用、告知紀錄、狀態管理、Reply 限制 | 未啟用不收錄；未註冊不執行智能查詢；所有失敗路徑不推播 |
| 2：可靠收錄與基本找回 | 文字、圖片及來源保存；附件工作狀態；全文／日期／發布者搜尋；撤回處理 | 不靠 AI 也能按條件找回原件；重送不重複；附件失敗可追查 |
| 3：智能搜尋 | 接入 Agents SDK、圖片辨識、語意搜尋、版本判讀、追問 | 能找出未註冊者貼的服事表；多版本不混淆；結果帶來源 |
| 4：附件與資料生命週期 | 擴展 PDF／Excel；受保護查看頁；保存期限、刪除與配額 | 不執行附件程式；過期／撤回資料不被搜尋提供；下載權限正確 |
| 5：Azure 備援與成本保護 | 故障切換、逾時、預算預留、限流、降級與用量報表 | 模擬 OpenAI 故障可在已驗證能力內備援；不重複外部操作、不突破預算、不推播 |
| 6：受控試用 | 少量已告知群組試用，收集搜尋正確率、延遲與成本 | 核心案例達標，確認收錄缺漏與成本後再擴大 |

階段 1 起就加入基本額度、去重與權限測試；階段 5 是完整化與故障驗證，不代表成本與安全控制延後才做。

## 十二、核心驗收案例

1. 未註冊成員貼圖，已註冊成員日後能找到。
2. 圖片未附「服事表」文字，仍能依圖片內容搜尋。
